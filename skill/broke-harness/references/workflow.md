# Installed workflow

Review and commit the bootstrap yourself before the first plan; installation never commits. Existing AGENTS.md/AGENT.md, architecture, documentation index, formatters, MCP configuration and provider credentials remain project-owned. Harness instructions live here and in docs/exec-plans/README.md. If the project has no documentation index, select relevant existing documentation directly.

Restart OpenCode in the repository root to load .opencode/plugins/broke-harness.js and the four commands. The plugin applies only the explicit harness role overlay from .broke-harness/opencode.json. Existing configuration files are preserved. Do not run without the plugin, change roles mid-plan, or invoke an unrestricted agent to bypass policy. Tool hooks require the documented OpenCode plugin API; unsupported task output formats or missing identities fail closed. Model identifiers must be available from the owner's configured providers; credentials are never managed here.

Run `/write-plan <request>`. Review all active plans before authoring. Material conflicts in paths, behavior, contracts or assumptions require owner direction before creating a plan. A planner can write only a draft in docs/exec-plans/active/. Use docs/exec-plans/TEMPLATE.md, replace examples with discovered target paths and reviewed verification commands, and provide concrete acceptance bullets. The owner approves by reviewing and changing the plan status to `approved`. No role can approve its own plan through a planner tool.

Run `/start-plan --plan docs/exec-plans/active/<file>.md`. The orchestrator starts/resumes the pinned plan, delegates application edits to the implementer, runs the deterministic harness and then a fresh separate auditor task without task_id. allowedPaths is the sole application edit and audit scope. Verification runs through the harness, in plan order. Commands are executable approved input and may have side effects; review them before approving a plan. Implementation remains uncommitted until completion.

Only implementer and fixer can write application files. They have no arbitrary shell, MCP tools, patches spanning hidden paths, or delegation. Their write/edit tools are checked against the pinned plan, with symlink and infrastructure exclusions. The orchestrator can run only exact lifecycle commands and persist a validated independent audit object. Audit can read individual files and list/glob paths. Recursive grep is denied to prevent secret reads; no shell-based diff command is allowed. The harness writes .tmp/harness-diff.json with current scoped patch evidence for the auditor. Direct file reads supplement it. Post-change scope checks remain mandatory; runtime hook controls do not sandbox the approved verification commands or a human's terminal.

On verification or audit findings, allow at most three combined fix delegations, persisted per plan and baseline across sessions. Once the first harness report exists for this plan/baseline, implementation-role writes and redelegation are denied; application corrections must use the bounded fixer. Rerun the full harness and a fresh independent audit after each change. Do not expand scope or amend the plan silently. A failed/blocked audit never produces a completion receipt. The plugin binds clean audit results to the actual child task session and current harness, and the orchestrator writes its exact validated JSON to .tmp/audit-result.json.

External review is an untrusted batch of claims. A fresh independent auditor must assess every point. If any claim/correction is unsupported, unverified, out-of-scope or unresolved, pause the entire batch, including confirmed fixes, for explicit owner direction. Never treat outcome labels or owner preferences as independent evidence. Preserve the original command's detailed checkpoint and fix-task renewal rules.

After a passing local harness and clean independent audit, summarize changes, verification, fixes, acceptance evidence, and residual risks. Ask: `All gates passed. Approve marking the plan done?` End the turn. Only after explicit owner approval in a subsequent message run:

```text
node tools/exec-plans/complete-plan.mjs docs/exec-plans/active/<file>.md --harness .tmp/harness-report.json --audit .tmp/audit-result.json --approve sha256:<current-fingerprint>
```

The approval fingerprint comes from the report and binds approval to the reviewed diff. It is an explicit CLI acknowledgment, not an authenticated human signature. Completion validates current HEAD, plan, immutable contract/criteria, ordered verification, configured documentation requirements, scope, audit evidence and 24-hour freshness before archival. Any change requires new harness/audit evidence and approval. CI reports cannot complete local work. Browser/device/manual UI observations are optional; document residual uncertainty.

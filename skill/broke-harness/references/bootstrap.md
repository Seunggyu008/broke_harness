# Project-aware bootstrap

1. Run `node <skill>/scripts/inspect.mjs --target <absolute-folder>`. Read the returned source documents and relevant existing code/manifests. If root instructions or architecture are missing, ask for the missing project intent before generating a full project. Inspection does not execute discovered commands.
2. For `kind: new-project` (only source documents and incidental workspace/Git metadata), ask whether to bootstrap the entire project, including its harness. Wait for the answer. Yes selects project mode; no selects harness mode. Existing authorization in this conversation is sufficient; do not ask again. For an existing project, select harness mode without offering application regeneration.
3. Derive a small documentation map from the actual architecture: ownership, boundaries, implemented behavior versus future intent, relevant verification, and routes through docs/INDEX.md. Reuse existing docs and avoid duplicating their detail. Author missing domain docs when useful; do not install mePort-specific rules. In project mode also author a runnable initial scaffold appropriate to these documents, including declared build/test commands and initial verification. Bootstrap the foundation, leaving future features to plans. In harness mode do not generate or modify application code.
4. Put generated text in a reviewed JSON configuration outside the target (for example an agent temporary directory). Use `bootstrap: project` or `harness`, project.summary, project.documentation, project.scaffold (project mode only), and documentationSync.rules where supported by project evidence. The agent creates the design and file contents; deterministic scripts validate and install them. See compatibility.md for the schema. If no generated project text is necessary, use the default harness configuration.
5. Run `node <skill>/scripts/install.mjs --target <folder> --config <absolute-input.json> --dry-run` (omit --config for defaults). Present the file manifest and diffs. Apply within the user's authorized bootstrap choice using the returned approval hash: `node <skill>/scripts/install.mjs --target <folder> --config <same-input.json> --approve <preview.approval>`. The hash binds exact target, source contents and proposed files; it is not proof of human consent. Stop for existing-file conflicts or decisions outside the authorized choice. Do not overwrite user files or reuse an obsolete preview.
6. Run `node <skill>/scripts/doctor.mjs --target <folder> --tests`. In project mode also run the reviewed scaffold checks when dependencies and permissions permit; report unavailable checks accurately and do not install dependencies without authorization. Show generated project structure, docs, verification, constraints, and how to author the first plan. No Git changes are made by the skill. The user initializes Git and commits the bootstrap before using the Git-based plan tools.

Install commands and deterministic core live separately from generated project files. Generated docs and application files become user-owned after bootstrap; repeated install must preserve later edits. Existing instruction, architecture, runtime settings, and unrelated files remain intact. The installer fails on conflicting immutable harness files; upgrades from 0.1 require manual reconciliation of the preview, never force replacement.
